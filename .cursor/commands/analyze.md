# 영향도 분석

공통 규칙(`.cursor/rules/harness-core.mdc`)을 따른다. 금지 행위와 근거 표기는 그 규칙을 참조하고, 여기서 반복하지 않는다.

역할: 수정 요청의 영향도를 기록한 뒤 **코드를 고치지 않고 멈춘다.**

입력: 이 Command 뒤에 오는 자연어 수정 요청.

## 절차

1. 요청이 모호해서 분석 대상을 정할 수 없으면, 추측으로 채우지 말고 먼저 질문하고 멈춘다.
2. 요청을 파악한다. `harness/records/<YYYY-MM-DD-짧은설명>/`를 만들고 `record.md`를 연다. 양식이 `harness/templates/record.md`에 있으면 그것을 따른다. 없으면 아래 구역 제목으로 만든다.
3. `src/` 안의 관련 코드를 **직접 열어 읽는다.** `.cursor/`, `harness/`는 근거로 쓰지 않는다. 대상이 `src/` 밖이면 분석을 이어가기 전에 개발자에게 확인을 받는다.
4. 요청이 **프로젝트 외부 사양**에 의존하는지 판단한다.
   - 호출함: 외부 라이브러리, 프레임워크(Spring Boot/Security 등), SDK, REST/OpenAPI, Maven/Gradle dependency, Docker image/Compose, 외부 제품·인프라(MinIO, Redis, MySQL 등), 환경변수 키, CLI, 버전/Deprecated/공식 설정 확인.
   - 호출하지 않음: 기존 Service 로직, DTO 필드, Mapper SQL, null/조건문, 내부 리팩터링만인 경우.
   해당하면 `.cursor/agents/external-researcher.md`를 호출한다. 반환된 `## 외부 사양 검증`을 `record.md` 영향도 분석 안에 그대로 기록한다. Researcher는 파일을 수정하지 않는다.
   `PARTIALLY_VERIFIED` / `NOT_VERIFIED`이면 채팅 요약과 승인 대기에 그 사실을 명시한다. 검증 못 한 값을 확정처럼 쓰지 않는다.
5. `record.md`에서 **이 단계 구역만** 채운다. 다른 구역은 비워 둔다.
   - 요청
   - 영향도 분석: 변경 대상, 직접 영향, 추가 확인 대상, 위험 요소, 항목별 근거, (해당 시) 외부 사양 검증
   - 예상 변경 파일
   모든 항목에 `[확인] 경로` 또는 `[추정]`을 붙인다. 외부 사양은 Researcher 검증 결과를 따른다.
6. 채팅에 요약을 짧게 보여준다. 넣을 것: 변경 대상, 주요 영향, 위험 요소, 예상 변경 파일, (해당 시) 외부 사양 검증 상태.
7. 개발자에게 **진행** 또는 **다시 분석** 중 무엇을 할지 묻고 멈춘다. `확인해`는 수정 승인이 아니다. 개발자 확인 구역은 비워 둔다. 결정이 오면 그때 기록한다.
